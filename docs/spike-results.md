# M1 device spike: results (2026-11-02)

What this is: a measured proof that the planned stack (Rust, `wgpu`, Lua via `mlua`,
`winit` + `android-activity`, `cpal`, and the C11 audio core) builds, runs and renders
2D + 3D on desktop and on the Android emulator. **It is not a device result.** The
Retroid Pocket 6 has not arrived; every number below comes from an Apple M4 Mac or
its emulator, both far faster than a handheld. Nothing here predicts handheld frame
rate, thermals, battery or audio latency.

Verified versions: `wgpu` 30.0.1, `winit` 0.30.13, `cpal` 0.18.2, `mlua` 0.12.2 (vendored
Lua 5.4), `gltf` 1.4.1, `glam` 0.34.2, `android-activity` 0.6.1, NDK r29, Rust 1.99.1.

## The test scene

Lua drives a car (steer/throttle/brake through an action layer); the engine draws
2D sprites behind a 3D scene and a debug HUD in front, in one render pass.

- 10,000 batched, textured, alpha-blended, rotating sprites (one instanced draw)
- 400 instanced low-poly cars (132 triangles each, about 53k triangles) plus a ground
  plane, palette-textured, lit by one directional light, depth-tested
- HUD text drawn with the sprite batch (about 1,500 extra sprites)
- Original car model generated by `scripts/gen_spike_assets.py` (GLB, imported by
  `model.rs`, which lists unsupported glTF features instead of dropping them silently)
- The C audio core's demo score rendering live through `cpal`
- Four draw calls per frame

## Results

### Desktop (macOS, Apple M4, Metal), release build, headless, 1920x1080

Offscreen rendering with a fixed 60 Hz step, timed **including GPU completion** each
frame (so these are real frame costs, not vsync-limited rates):

| Sprites | Cars (triangles) | Mean ms | p95 ms | Max ms |
| ---: | ---: | ---: | ---: | ---: |
| 10,000 | 400 (53k) | 1.20 | 2.45 | 11.3 |
| 50,000 | 400 (53k) | 2.62 | 3.98 | 19.4 |
| 100,000 | 400 (53k) | 4.29 | 4.81 | 31.8 |
| 10,000 | 2,000 (264k) | 1.59 | 3.40 | 10.2 |
| 100,000 | 2,000 (264k) | 4.58 | 5.38 | 30.4 |

Max values include first-frame pipeline and buffer warm-up. Windowed on the same Mac
(vsync, ProMotion 120 Hz display) it held a steady 120 fps with audio running
(48 kHz stereo F32).

### Android emulator (arm64, Android 13, 1920x1080 profile `retroid-sim`)

Release APK, built without Gradle (`scripts/build-apk.sh`, 7.9 MB), installed with `adb`.

- **Host-GPU mode** (`-gpu host`): `wgpu` selects Vulkan ("Apple M4", virtual GPU, via
  the emulator's translation layer). A steady **60 fps** (vsync); CPU time to encode and
  submit about 1.1 to 2.0 ms per frame; Lua about 0.02 ms; audio started at
  48 kHz / 2 ch / F32, callbacks maxing at 1.6 ms, zero core faults, zero stream errors.
  The screenshot matches the desktop render.
- **Software mode** (default `-gpu auto`): adapter is `llvmpipe`, a CPU rasterizer, giving
  roughly 27 to 34 fps. This only shows the app also runs on a software Vulkan driver.

### Tests

16 Rust unit tests (glTF import, font, Lua host including hot reload, Lua stdlib
hardening, audio FFI, perf summary) and the 7 audio-core C tests pass.

## What was proven

- Rust to Android works end to end: `cargo-ndk` library, `aapt2`-built manifest,
  `zipalign`, `apksigner` (v2/v3 verified), NativeActivity with no Java or Kotlin.
- `wgpu` runs on Android through Vulkan, with OpenGL ES as a coded fallback (backend order
  Vulkan then GL). The GL path hit an over-strict limits request in the emulator; it now
  requests GLES-3.0-class limits. The GL path has not been re-run on Android since the fix.
- `mlua` with vendored Lua 5.4 compiles for Android with the NDK and runs the same script.
  The Lua environment is reduced to math/string/table/utf8/coroutine; `io`, `os`,
  `package`, `debug`, `dofile`, `loadfile` and `require` are absent (tested). This is a
  stability boundary for hand-written games, not a hostile-code sandbox: there are no
  time or memory limits yet.
- The C11 audio core links into the Rust runtime through `cc` and a small FFI layer and
  renders live on Android (AAudio via `cpal`).
- One render path draws 2D and 3D in a single pass; the same code renders a window, an
  offscreen target and a captured PNG.
- Script hot reload on desktop works, and a bad edit reports an error while keeping the
  last good state.

## Open findings (carry into M2)

1. **System bars.** On the emulator the surface was 1920x944: a status-bar-sized strip
   at the top stays black and a gesture handle shows. Setting the `FULLSCREEN` window flag
   did not change it on this profile. Needs immersive mode properly (display cutout mode
   in a theme resource and/or hiding the system bars through JNI). The Retroid's screen is
   believed to be a plain 16:9 panel with no cutout; verify on the device.
2. **Gamepad on Android.** `winit` delivers game-controller buttons only as key events
   with native codes (mapped: D-pad, A/B/X, L2/R2), not analogue sticks or triggers.
   Desktop gamepads work through `gilrs`. Android needs a native-activity input path
   (own event loop or an input hook) before analogue steering works. High priority for a
   handheld.
3. **Touch and keyboard on Android** are implemented but were not exercised (no input was
   injected into the emulator).
4. **Audio latency** is not measured. Only callback processing time is (about 1.6 ms max
   on the emulator). Device latency, underruns and Bluetooth behaviour need hardware.
5. **Android lifecycle** (pause/resume, surface loss, rotation, process death) is handled
   in code (surface dropped on suspend, rebuilt on resume) but not exercised.
6. **Text and layout.** The HUD uses a debug pixel font. Real font rendering, text
   layout and scaling for the logical-540-high coordinate space are M2 work. The resolution
   policy (logical units, pixel-art mode, native-resolution UI) is still an open decision.
7. **Frame pacing** is only observable through vsync here. No GPU timestamps yet (not
   guaranteed on mobile GPUs); consider them as an optional feature in M2.
8. The release library is not stripped beyond debug info; size optimisation (and `.so`
   alignment checks for newer Android page sizes) belongs to M3.

## Gate status

**Provisionally passed on desktop and emulator; the device gate is still open.** Nothing
found so far argues for the C + SDL3 fallback. The decision is final only after the same
APK runs on the Retroid Pocket 6 with a controller, a 10-minute thermal run and a look at
audio latency. If it does not hold up there, the recorded numbers above are the baseline
to compare against.

## Reproduce

```sh
scripts/env.sh cargo run --release -p nova-runtime --bin nova -- --headless --frames 300 --size 1920x1080 --capture build/spike.png
scripts/env.sh cargo run --release -p nova-runtime --bin nova                 # window; Esc quits
scripts/env.sh cargo run --release -p nova-runtime --bin nova -- --script crates/nova-runtime/assets/spike/main.lua   # hot reload
scripts/build-apk.sh                                                          # build/android/nova-spike-debug.apk
scripts/env.sh emulator -avd retroid-sim -gpu host                            # then: adb install -r ... ; adb shell am start -n com.nova.spike/android.app.NativeActivity
scripts/env.sh adb logcat -s nova                                             # per-second stats
```
